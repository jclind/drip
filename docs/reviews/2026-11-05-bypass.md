# Ways around drip's limits, 2026-11-05

A review of every way a user who installed drip could get unlimited YouTube without uninstalling or disabling it. Written the day before the Chrome Web Store publish, against `main` at `be8ab2b`. Review only: no code, config, or tests changed.

How it ran: three read-only reviewers split the code. One took hosts, URL shapes, and players other than the main one; one took the rules and the worker (`state.js`, `background.js`, Settings); one took the watch page at run time. Claude then read the code behind every finding and re-ran the rule findings in Node against the real `state.js`. CLAUDE.md, DESIGN.md, RELEASE-PLAN.md, AUDIT.md, IDEAS.md, and `store/` were read first, so known and accepted items are left out or marked.

YouTube wasn't reachable from the review container. So "confirmed" means the code does it and a Node run or the watch-page harness shows it. "Plausible" means the code allows it but it depends on how live YouTube behaves, which nobody checked.

## What should block tomorrow's publish

1. **Setting the OS clock back reopens the first day** (finding 1). One clock change, then Watch time off, for good.
2. **Dry hours give back more drops than were bought** (finding 2). A Settings-only loop, every day, about 2x the allowance at defaults and about 6.5x with "Save unspent for" at 7 days.
3. **Grace never ends on a live stream, a looped video, or a paused one** (finding 3). Unlimited watching once grace mode is on. The fix that caps grace at what's left of the video keeps Q3 as written; the several-tabs part is an open question.
4. **The trailing-dot host, if YouTube serves it** (plausible P1). Ten seconds to check by hand: open `https://www.youtube.com./`. If YouTube loads, drip doesn't run there at all.
5. **Hover previews, if they play whole videos** (plausible P2). Check by hand on a search page at 0 minutes.

Findings 1 to 3 have small fixes in `state.js` and `watch.js`. P1 and P2 need the manual check first.

## Confirmed

### 1. Setting the OS clock back reopens the first day, so every loosening applies at once

- **Where:** `src/lib/state.js:869-873`. `firstDayUntil` returns a time whenever `now < installedAt + 24h`, with no lower bound, so any date before install counts as the first day. `updateSettings` (`state.js:886`) and `allowChannel` (`state.js:1521`) trust it.
- **Trigger:** set the computer's clock to any past date, say 2020. Open drip's Settings. It even says changes apply at once. Turn Watch time off, or set 48 drops of 120 minutes, and allow 5 channels. Put the clock back.
- **Free watching:** unlimited, permanently, in about a minute. The first-day rule also moves today's balance, so 4 to 48 drops a day adds 44 drops on the spot.
- **Evidence:** `firstDayUntil(state, 2020-01-01)` is nonzero and `updateSettings({ clock: false, watchTokensPerDay: 48 })` returns `applied: { clock: false, watchTokensPerDay: 48 }, pending: {}`. The rules reviewer got the same result through the real `background.js` loaded as a store build.
- **Fix:** keep a high-water mark of the latest time any message has seen (`maxSeenAt`) in state. The first day is over once `maxSeenAt` passes `installedAt + 24h`, or whenever `now < installedAt`, and a `firstDayOver` flag keeps it over. The same mark fixes findings 4 and 5.
- **Blocks publish:** yes. It undoes Q6 for anyone who knows how to change a clock, and the fix is a few lines.

### 2. A Dry hours refund counts drops at today's minutes per drop, not at what they were bought for

- **Where:** `src/lib/state.js:728-743`. `giveBack` takes `per = state.settings.minutesPerToken * 60` (line 730) and gives back `floor(minutes left / per)` drops up to the cap. Lowering minutes per drop tightens, so it applies at once. Turning Dry hours on over the current hour also applies at once (`updateDry`, `state.js:757` onward), and the worker runs `enterDry` after every message (`background.js:174`), so the refund comes on demand.
- **Trigger, every day:** keep 8 or more minutes unwatched. In Settings set minutes per drop to 1, which applies now, then back to 15, which waits for the reset. Then either wait for Dry hours to start, or turn Dry hours on for just the current hour. With the default reset at 4am inside the default 11pm to 6am Dry hours, the drops are worth 15 minutes again by morning.
- **Free watching:** the refund fills the drop counter to its cap. In a six-day Node run at default settings, watching came to 112 minutes a day against a normal 60. With "Save unspent for" raised to 7 days, a legal setting that waits once, it came to 392 minutes a day. Minutes that Q11 says expire at the reset turn into drops too.
- **Evidence:** 8 minutes left, minutes per drop set to 1 then 15, Dry hours start: `drops 8, minutes left 0`. Next morning: `8 drops x 15 = 120 minutes`. The rules reviewer found the on-demand form: one unwatched 15-minute drop came back as 15 drops with rollover at 7.
- **Fix:** give back at most the drops bought since the last reset, valued at their purchase price. For example, `min(floor(left / perAtPurchase), drops bought today)`, with `perAtPurchase = watchSecondsBought / drops bought today`, kept in state at each `spendWatch`.
- **Blocks publish:** yes. It needs nothing but Settings, it repeats every day, and Dry hours is new in this release.

### 3. Grace never ends on a live stream, a looped video, or a pause, and every playing tab gets it

- **Where:** `src/content/watch.js:168-177` (`setGrace`, `inGrace`), `:357-366` (`onEnded` is the only end), `:405-408` (`applyStatus` skips the lock in grace), `:517` and `:1319` (grants), `:1340` (navigation clears it). `inGrace` checks only the video id. No duration budget, no live check, nothing on pause.
- **Trigger:** turn on "Finish the current video". It waits for the reset, as it should. Then any of these:
  - With a few seconds left, play a 24/7 live stream or a 10-hour video.
  - Right-click the player and turn on Loop. A looping video never fires `ended`.
  - Open 4 long videos in 4 tabs, play them all as the minutes run out, pause them all, and watch each one later. Each tab keeps its grace while paused.
- **Free watching:** unlimited for one video per run-out, and each drop bought gives another run-out. In the watch-page harness, a 2-second balance played 3,600 seconds with no lock, and four tabs paused for 2 hours then played 4 x 3,600 = 14,400 seconds free.
- **Fix:** when grace starts, give it a budget of the video's `duration - currentTime` plus a small margin, spent as played wall time. Give live streams and unknown durations no grace, or a fixed cap. End grace after a long pause, a minute or so. Ending grace in other tabs reverses AUDIT finding 13's fix, so that part is under open questions.
- **Blocks publish:** yes for the budget. "Finish the current video" (Q3) doesn't cover a stream with no end or a loop. The several-tabs part can wait for Jesse.

### 4. Moving the OS clock forward a day refills, and moving it back keeps the refill

- **Where:** `src/lib/state.js:275-302`. `rollDay` adds a day's drops, clears unlocks, and applies everything waiting for the reset, and line 277 never moves `state.day` back.
- **Trigger:** set the clock a day ahead, open the popup or YouTube, set it back, buy drops. Then set it two days ahead, and so on.
- **Free watching:** 4 drops, 60 minutes, per jump, with no limit in one real evening. In Node, three jumps gave 20 drops instead of 8. It's borrowing: `state.day` ends up days ahead, so no reset comes until real time catches up. But nothing caps how far ahead you can borrow. That's the debt mode IDEAS.md ruled out because "it's easy to talk yourself past at 1am". A jump also applies any waiting loosening early, Watch time off included.
- **Fix:** with finding 1's `maxSeenAt`, refuse spending, unlocks, and Settings saves while `now` is more than a few minutes behind it. A jump forward then only works if the clock stays wrong. A trusted clock is the full fix: the worker could read the `Date` header from a `fetch` to youtube.com, which its host permission already covers. That changes Q4's honor system, so it's under open questions.
- **Blocks publish:** no on its own. It's borrowing and takes repeated clock changes. Ship the `maxSeenAt` guard with finding 1 if it fits.

### 5. "I need this one" used with the clock set back is logged in the past, so it never counts

- **Where:** `src/lib/state.js:627` logs `at: now`. `weekUses` (`state.js:791-803`) only counts uses from the last 7 x 24 hours. `Math.min(at, now)` handles a clock moved back after a use, not before.
- **Trigger:** set the clock months back, use 3 unlocks, move 8 days forward (still in the past), use 3 more, repeat, then put the clock back.
- **Free watching:** any number of free videos until the next real reset, during Dry hours too. In Node, 12 unlocks went through and real time still showed 3 left.
- **Fix:** log `at = max(now, maxSeenAt)` and refuse unlocks while the clock is behind `maxSeenAt`, as in finding 4.
- **Blocks publish:** covered by finding 1's fix if that uses `maxSeenAt`; not separately.

### 6. Changing the time zone gets past Dry hours, and an eastward zone resets the day early

- **Where:** `src/lib/state.js:150-154` (`dayKey`) and `:662` (`dryAt`). Both read local hours from whatever zone the computer is set to now.
- **Trigger:** at 11:30pm with Dry hours from 11pm, switch the computer to Pacific/Honolulu, where it's 9:30pm, then buy drops and watch. Switch to Pacific/Kiritimati at noon to roll to tomorrow early.
- **Free watching:** no Dry hours on any night the user wants. The early reset is borrowing, as in finding 4.
- **Fix:** save the IANA zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`) when Dry hours or the reset hour are set, and work out hours and `dayKey` in that zone with `Intl`. A real move to a new zone is then a Settings change, which waits under Q6.
- **Blocks publish:** no. It needs an OS change every night, and the fix touches every time rule.

### 7. An import can allow 20 channels, because each allow entry holds up to 4 ids

- **Where:** `src/lib/state.js:1417` (`cleanIds` keeps 4), `:1328` (`importData` passes the file's entry to `allowChannel`), `:1495-1497` (`allowCount` counts entries, not channels), `:1630-1632` (`allowedNow` frees any id in an entry).
- **Trigger:** Export, then edit `channels.allow` into 5 entries like `{"ids": ["@a", "@b", "@c", "@d"], "name": "x"}`. Import. Wait for the reset.
- **Free watching:** every video from 20 channels, all day and in Dry hours, instead of 5. In Node: `entries 5, channel ids allowed 20`, and a video from the third id of the fourth entry came out free.
- **Fix:** in `importData`, keep at most one handle and one `UC...` id per allow entry, or only the handle and let `lookUpChannel` fill in the id. Or count distinct handles in `allowCount`.
- **Blocks publish:** no, but it's a one-line fix and worth taking.

### 8. The watch page keeps playing while the worker refuses ticks

- **Where:** `src/content/watch.js:520`. On a failed tick it re-applies the page's own cached balance, which still has minutes, so nothing locks. A worker that never answers is handled (`:434-438` pauses after 5 seconds); one that answers with an error isn't.
- **Trigger:** anything that makes saves fail. The one a user can reach: the "I need this one" reason and title have no length cap (`state.js:619-628`) and the manifest has no `unlimitedStorage`, so a reason of several MB pushes state toward `chrome.storage.local`'s 10 MB quota. Getting close enough that later saves fail is fiddly.
- **Free watching:** unlimited while saves fail. In the harness, 1,800 seconds played on a 60-second balance and nothing was charged.
- **Fix:** fail closed. Pause once unsent seconds pass the page's `secondsLeft`, or after about 5 seconds of failed ticks, the way the no-answer case already does. Cap reason and title at about 500 characters in `needThis`.
- **Blocks publish:** no. The trigger is contrived, though the reason cap is a two-line fix.

### 9. Reloading or closing a tab drops up to 5 seconds of unsent time

- **Where:** `src/content/watch.js:79` (`SEND_EVERY = 5`) and `:1346`. There's no `pagehide` flush.
- **Trigger:** play 4 seconds, reload, repeat.
- **Free watching:** up to 5 seconds per reload, about 1 second near zero, where it sends every tick. Each reload costs a page load and often a preroll ad, so it isn't a practical way to watch. DESIGN.md already mentions the 5 seconds for menu links.
- **Fix:** mirror `unsent`, with its keys, to `sessionStorage` on every bank and resend it on the next load. The keys already stop a double charge.
- **Blocks publish:** no.

### 10. A muted video in a hidden tab or picture-in-picture locks up to a minute late

- **Where:** `src/content/watch.js:1346`. One `setInterval` drives both sending and the run-out check. After 5 minutes hidden and silent, Chrome's intensive throttling runs timers once a minute. Time is still measured in full with `performance.now()`, so it's charged; only the lock is late, and closing the tab then drops up to 60 seconds.
- **Trigger:** play muted in a background window or in picture-in-picture for over 5 minutes, then let the minutes run out, or close the tab.
- **Free watching:** up to 60 seconds per run-out or close. Harness: 60 seconds played on a 20-second balance. Whether Chrome throttles a page in picture-in-picture wasn't checked.
- **Fix:** also run the run-out check and the send from the video's `timeupdate` event, which the media pipeline fires about 4 times a second regardless of timer throttling.
- **Blocks publish:** no.

### 11. A waiting reset hour change can make a one-hour day

- **Where:** `src/lib/state.js:276-281`. `rollDay` finds the new day with the old hour, then applies a waiting `resetHour`.
- **Trigger:** with the reset at 11pm, set midnight and wait. Drops refill at 11pm and again at midnight.
- **Free watching:** one day's drops up to 23 hours early, once. Going back costs a long day, so there's no net gain over time.
- **Fix:** when a waiting `resetHour` applies, set `state.day` to `dayKey(now, newHour)` if that's later, the way the first-day rule already does.
- **Blocks publish:** no.

## Plausible: the code allows it, live YouTube decides

### P1. The trailing-dot host skips drip entirely

- **Where:** `manifest.json:35-77`. Every match is `https://www.youtube.com/*`, and `redirect.js:28` and `state.js:1056`, `:1068` compare hostnames exactly. Chrome treats `www.youtube.com.` as another host, so no content script runs there: no guard, no clock, no redirect, no hidden feeds. `redirectTarget` returns `''` for it.
- **Trigger:** type `https://www.youtube.com./watch?v=<any id>`. YouTube's own links keep the dot.
- **Free watching:** unlimited, any video, with the home grid and Shorts back. The user is signed out there, which doesn't stop public videos.
- **What decides it:** whether Google's servers answer the dotted host. It was the widely shared "add a dot after .com" ad-block trick in late 2023.
- **Fix:** if it loads, a `declarativeNetRequest` rule that redirects `www.youtube.com.`, `m.youtube.com.`, and `www.youtube-nocookie.com.` to the plain host, with host permission for the dotted hosts. Check whether Chrome accepts a match pattern with a trailing dot, and whether the store review asks about the extra permission.
- **Blocks publish:** yes if the page loads.

### P2. Hover previews may play whole videos with no clock

- **Where:** `src/content/guard.js:12` refuses play only for `#movie_player video`, and `watch.js:446` pauses only `#movie_player`'s video off `/watch`. Nothing in `src/content/` or `early.css` touches `ytd-video-preview` or the inline preview player.
- **Trigger:** search for a video, or open History or Watch later from drip's menu. Hover a thumbnail, unmute the preview, and leave the pointer still. Zoom the page to make it bigger.
- **Free watching:** unlimited, any video search can find, in a thumbnail-sized player, at 0 minutes and in Dry hours.
- **What decides it:** whether desktop inline playback runs to the end with unmute and seek, and whether it uses its own player element. If it reuses `#movie_player`, the tick pauses it within a second and this goes away.
- **Fix:** hide `ytd-video-preview` and its player in `early.css`. As a backstop, have `guard.js` refuse play for any media element on youtube.com that isn't the main player while the clock is on, keeping the `data-drip-broken` fail-open, and have `watch.js`'s tick pause one. That one rule also covers P5.
- **Blocks publish:** yes if a preview plays to the end. Check at 0 minutes on a search page.

### P3. A stale owner row during an in-page move could free the new video for the day

- **Where:** `src/content/watch.js:32-34, 204-211, 226-249`; `src/lib/state.js:1638-1650`. The only proof that the owner link belongs to the new video is `ytd-watch-flexy[video-id]` matching the URL. The comment says the two change in the same frame, checked once on air on 2026-11-03.
- **Trigger:** watch a video from an allowed channel, then move in the page to any other video: a search result, a description link, the next in a playlist.
- **Free watching:** if the owner row lags the flexy's `video-id` even once, the new video goes into `allowedToday` and is free for the rest of the day, and nothing ever corrects it. The harness shows that result once the stale link is read.
- **What decides it:** whether YouTube ever updates the flexy's id before the owner row: a slow `/next` response, Back and Forward, playlist advance, a narrow layout.
- **Fix:** have the worker confirm before writing `allowedToday`. It can fetch `https://www.youtube.com/oembed?url=https://www.youtube.com/watch?v=ID` and compare the `author_url` handle, which the existing host permission covers, as `lookUpChannel` already does for channel pages. At least, require the same reading on two ticks after the title changes.
- **Blocks publish:** no, but test it on air before turning the allow list loose on strangers.

### P4. `/watch` with no `v`, or with two, can charge nothing or the wrong video

- **Where:** `src/content/watch.js:153-157` and `early.js:41-43` read only the first `v` in the URL. `watch.js:271-275` sets `runId` once at play, and `bank` drops time with no `runId` (`:319`).
- **Trigger:** open `/watch?list=<playlist>` with no `v` and don't pause. Or, after unlocking video A with "I need this one", open `/watch?v=A&v=<any>`.
- **Free watching:** unlimited, any video, if YouTube plays without a `v` in the URL for a while, or plays the second `v`.
- **What decides it:** whether YouTube adds `v` with `replaceState` and no `yt-navigate-finish`, and which `v` it plays.
- **Fix:** take the playing id from `ytd-watch-flexy[video-id]` or the player, not the URL, and update `runId` on every tick while playing. Treat a video as free only when the flexy's id equals the URL's.
- **Blocks publish:** no.

### P5. A channel's featured video or trailer may play with no clock

- **Where:** as in P2, only `#movie_player` is held or paused. `channel.js` doesn't touch the player.
- **Trigger:** open any channel's Home tab and play its trailer, or its featured video if subscribed.
- **Free watching:** one or two videos per channel, any length, across as many channels as you like.
- **What decides it:** whether `ytd-channel-video-player-renderer` uses its own player. If it's `#movie_player`, the tick pauses it every second, which breaks it but leaks nothing.
- **Fix:** the guard rule in P2, or make the featured player a link to `/watch`. Q16 leaves channel pages as they are, so this one is Jesse's call.
- **Blocks publish:** no.

### P6. Unusual Shorts paths aren't redirected

- **Where:** `src/lib/state.js:1047` and `:1070`. The rules are case-sensitive and anchored. In Node, `/Shorts/ID`, `//shorts/ID`, `/%73horts/ID`, and `/shorts/ID/x` all return `''`, and so do `/Feed/Subscriptions` and `/TV`.
- **Free watching:** endless Shorts, if YouTube renders any of those paths. The Shorts player isn't `#movie_player`, so nothing meters it.
- **What decides it:** whether YouTube's router ignores case, extra slashes, or escapes. It probably doesn't.
- **Fix:** lowercase, collapse slashes in, and decode the path before matching, and send any page that has a Shorts player to `/watch`.
- **Blocks publish:** no.

### P7. A page restored from the back/forward cache keeps its old state

- **Where:** `src/content/watch.js:1305-1349` and `early.js:103-123` have no `pageshow` handler, so storage events missed while the page was cached never arrive.
- **Trigger:** watch with minutes left, go to another site, use the minutes up in another tab, press Back, press play.
- **Free watching:** up to about 5 seconds per restore, until the first tick reply locks it.
- **Fix:** on `pageshow` with `persisted`, pause, ask the worker for status, and re-run early.js's check from `chrome.storage.local.get`.
- **Blocks publish:** no.

### P8. `/live/ID`, `/clip/ID`, and top-level embed playlists aren't mapped

- **Where:** `src/lib/state.js:1060-1073`. `/embed/videoseries?list=...` becomes `watch?v=videoseries`, `/embed?list=...` and `/live/ID` and `/clip/ID` aren't handled.
- **Effect:** if YouTube keeps those paths in the address bar, `watch.js:446` pauses the main player every second. That leaks about a second per press of play and, worse, makes shared `/live/ID` links unwatchable even with minutes left. Mostly a usability bug.
- **Fix:** map `/live/ID` to `/watch?v=ID`, and decide what clips and embed playlists should do.
- **Blocks publish:** no.

### P9. Some topic feeds aren't replaced

- **Where:** `src/lib/state.js:1047` lists only two topic channel ids. Direct links to the Gaming, Sports, News, Live, and Learning topic channels, and `/source/ID/shorts`, still show a feed of anyone's videos. Every video there is still charged, so this is a feed leak, not free watching.
- **Fix:** add the topic channel ids and `/source/`.
- **Blocks publish:** no.

### P10. `?app=m&persist_app=1` may bounce between hosts

- **Where:** `src/lib/state.js:1056-1058` keeps the query when moving `m.` to `www`. If www honors `app=m` and sends the browser back to `m.`, the tab loops. A broken tab, not free watching.
- **Fix:** drop `app` and `persist_app`, or set `app=desktop`, when rewriting.
- **Blocks publish:** no.

## Rejected, with reasons

- **Media keys, Chrome's media controls, the play button in picture-in-picture, the native context menu's Play.** They can get past `guard.js` through Chrome's own play, but `early.js:86-95` pauses on `play` in the capture phase, `watch.js:346-352` pauses on `playing`, and the tick re-pauses every second. Nothing measurable gets through.
- **YouTube's keyboard shortcuts and clicks under the lock.** `guard.js` refuses YouTube's own `play()` while the page is held, and the overlay covers the player.
- **The miniplayer.** `early.css:68` hides it and `watch.js:446` pauses the main player off `/watch` every second.
- **Autoplay and Mixes.** `autoplayOff` (`watch.js:143-146`) clicks the switch off every tick, and each next video in a playlist or Mix is a `/watch` navigation with its own clock. Playlists continuing is Q2.
- **Grace on reload, playlist advance, or leaving and coming back.** `watch.js:1340` and the reload both clear it, and Dry hours end it through `graceAllowed`.
- **Two paid tabs playing together for the price of one.** By design, in DESIGN.md "The clock with several tabs".
- **A clock dragged back slowly during play.** It saves only the seconds pulled back, about 16 seconds charged for 60 at minus 4 seconds every 5. Not doable by hand. A clock moved back by more than a tick clears the marker and charges in full.
- **Fake `ago` or `seconds` in a tick.** Both are clamped, late time is charged in full, and only drip's content scripts on www.youtube.com can send a tick (`background.js:450-453`).
- **Developer mode and the dev clock in a store build.** `bin/build-release` strips `src/devpanel` and `externally_connectable`. Loaded as a store build, the worker refuses `devAction` and `setDevMode`, and `importScripts('devpanel/clock.js')` falls back to real time.
- **Importing `installedAt`, `tokens`, `unlocked`, `day`, or `firstDayOff`.** `importData` ignores them, skips today's log and days already there, and never touches balances. Imported "I need this one" uses can only use up the weekly count.
- **Reset handing back drops.** Defaults that loosen wait, balances stay, and the log stays.
- **Name matching on cards.** `freeToStart` matching by name only skips buying a drop; the watch page still locks without an id match.
- **"I need this one" on the same video with `&t` or `&list`.** The same id stays unlocked, as intended; other videos in the playlist lock.
- **Counting normal playback as an ad.** Only YouTube sets `ad-showing`, and time is split at every change. Side-by-side ads on live streams weren't checked live.
- **The hidden Subscriptions frame.** It has `pointer-events: none` and opacity 0, it's removed when the read ends, and drip's scripts don't run in it.
- **A cycle of reset hour changes for extra resets.** Each logical day is one calendar date, so over time there's one reset per date. Finding 11 is the one-off borrow it allows.
- **Playback speed.** At 2x, a 15-minute drop holds 30 minutes of video. That matches Q10's "drained only while playing". It's under open questions, not a bug.
- **Accepted already:** embeds on other sites (Q7), music.youtube.com (Q19), incognito, other Chrome profiles, and the phone app (IDEAS.md), DevTools and bookmarklets (Q4), the stale-reply race (IDEAS.md "Known races"), and everything in AUDIT.md.

## Open questions for Jesse

1. **Grace across tabs.** AUDIT finding 13 gave every playing tab grace. With finding 3's budget, should a pause still keep grace, and should only the tab that ran out get it?
2. **A trusted clock.** Should drip roll days and judge the first day by YouTube's server time, read from the `Date` header of a `fetch` the host permission already allows, instead of the computer's clock? It would end findings 1, 4, 5, and 6 at their root, but it moves away from Q4's honor system and needs the network for the reset.
3. **Time zone.** Should Dry hours and the reset hour follow the zone they were set in (finding 6), so travel becomes a Settings change that waits?
4. **Q7 and Q19 for strangers.** Both are one URL away: `music.youtube.com/watch?v=<any id>` likely plays any video in video mode, and an embed works on many sites. Still fine for a public build, or worth a line in the store listing?
5. **Channel pages' featured player (P5).** Q16 leaves channel pages alone. Is a trailer playing free fine, or should it link to `/watch`?
6. **Playback speed.** Charge `max(1, playbackRate)` times wall time, or leave it?

## How another agent can check this

- Findings 1, 2, 4, 5, 7, and 11: load `src/lib/state.js` in Node with `require` and call the rules with chosen `now` values. For finding 2, start from a state installed 30 days ago, `updateSettings({ dryHours: true })`, spend every drop, `charge` all but 8 minutes, `updateSettings({ minutesPerToken: 1 })`, then `({ minutesPerToken: 15 })`, then `enterDry` at 11pm. The result is a full drop counter and no minutes. For finding 1, `firstDayUntil(state, new Date(2020, 0, 1).getTime())` is nonzero.
- Findings 3, 8, 9, and 10: copy the fake page from `test/watch.test.js` and drive `watch.js` with fake timers. Don't edit the test file.
- P1, P2, P5: on a Chrome with the store build loaded and 0 minutes left, open `https://www.youtube.com./`, hover a search result and unmute it, and play a channel's trailer. Each one that plays past a few seconds is confirmed.
- P3: with an allowed channel, move in the page from its video to another channel's video many times, with the network throttled in DevTools, and watch `allowedToday` in the dev panel.
